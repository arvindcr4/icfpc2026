# history.man — output the ICFP history text

**Problem.** No input. Output the 2810-byte ASCII string in
`icfp-history.txt` (conference locations and Most Influential Paper
winners, 1996–2026). Footprint-scored: **score = max(width, height)²**,
smaller is better; speed is irrelevant.

Generated by `gen_history.py` (`uv run python solutions/gen_history.py`
rebuilds and sim-verifies it). **92 × 88, score 8464**, halts on its own
at tick 56 246. Accepted by the official judge on 2026-07-25 (submission
`cb784caf`, 1/1 cases).

## Idea: the program text is the tape

Room cells store at most one decimal digit each (~3.3 bits), so the text
— every char in ASCII 32..122 — is packed as base-95 number literals,
costing ~2 digit cells per character instead of ~5 cells for a
one-literal-per-char approach. Each *chunk* encodes m ≤ 9 chars:

```
value = Σ (char_j − 31) · 95^j        (j = 0 is the first char out)
```

Two deliberate choices:

- **Offset −31, not −32.** Digits land in 1..95, so no base-95 digit is
  ever zero. Decoding can emit on every divmod step and stop exactly when
  the quotient reaches 0 — the stream is self-delimiting, high-order
  spaces survive, no sentinel digit is spent, and the value `0` is free
  to mean end-of-stream.
- **9 chars per chunk.** 95⁹ < 10¹⁸ < 2⁶³, so every literal fits a
  64-bit integer read in *both* directions — the official loader rejects
  literals that overflow either way, and 64-bit is confirmed by the
  Language Reference ("every value is a signed 64-bit integer"). Full
  chunks are exactly 18 zero-padded digits, so a chunk-plus-send is a
  fixed-size cell slot and rows pack uniformly.

## The layout constraint that rejected v1: column backtick pairing

The official loader pairs backticks **per row and per column
independently** (Language Reference "fine print"; see PATTERNS.md). The
first submission packed `` `…`s `` at 21 cells/chunk with identical
geometry on every row: backtick columns lined up, right-to-left rows put
an `s` between two vertically paired backticks, and the load was
rejected (`expected a digit or a space between backticks … at (2, 2)`) —
our sim reads literals only along the walk and accepted it.

The fix is a fixed 22-cell **slot** per chunk with the two walk
directions offset inside the slot:

```
rightward row:   `18 digits`s␣
leftward  row:   ␣s`sredro-klaw ni stigid 81`
```

Per column the union is: backticks over backticks (vertically adjacent →
legal empty literals), `s` over digits, spaces over spaces — no op ever
sits between a vertical pair. Both directions still carry 4 chunks per
row; the cost is 1 pad cell per chunk (width 88 → 92, score 7744 → 8464).
`analyze.backtick_issues` (also in `littleman check`) validates the rule
statically, and the generator refuses to write a violating grid.

## The grid

```
+------------------------------------- 92 wide ---+
|@`496065010874964263`s `443079475444…           v|   producer: 79 rows,
|v s`…` s`…` s`…` s`…`                            <|   serpentine walk,
|>`…`s `…`s `…`s                                 v|   4 slots per row
|            …  (313 chunks total)  …             |
|>`282300000000000000`s 0sH                       |   last chunk, then
+--------------------------------------------------+   0-sentinel, halt
 v+---------------+  +---------+
 >|@>rX`1`NsH     |  |@`31`M v |
  | ^            <|  |>      v |
  |   >W`95`W/XWs^|  |       r |
  |   ^    WsW<   |>>|      vXH|  +-+
  +---------------+  |^   s+<< |>>|O|
      man 1          +---------+  +-+
                         man 2
```

**Producer** (top room). One man snakes over 313 literals, `s`ending each
into the pipe down to man 1 — the room's single outgoing pipe, so every
`s` targets it wherever the man stands, and rows need no pipe plumbing.
Digits are written in walk order (reversed on right-to-left rows) inside
fixed 22-cell slots (see above); turns live in two reserved edge columns.
When the pipe is full the producer just blocks. After the last chunk:
`0 s H` (the generator asserts the terminator lands on a rightward row —
its cells were checked against the slot columns only for that case).

**Man 1 — unpacker.** Outer loop `>rX`: fetch a chunk, and since every
real chunk is positive, `X` is a two-way branch — `0` falls straight into
`` `1`NsH ``: send −1 downstream, halt. The divmod row `>W`95`W/X` leaves
quotient in `A`, remainder in `B`:

- **q > 0** (more chars): turn down into `W s W` — send the remainder
  *from the off hand*, restoring the quotient to `A` — and loop.
- **q = 0** (that remainder is the chunk's last char): fall into `W s ^`
  and ride the return row back to the outer `r`.

There is deliberately no `+31` here: adding 31 while keeping the
quotient would need a third register, i.e. a storage-pipe round trip per
character. Shipping the raw 1..95 digit downstream avoids it.

**Man 2 — +31 emitter.** `` `31`M `` once, then `r X + s` forever: `r`,
`+`, `s` never write `B`, so the constant lives in the off hand for all
2810 characters. `X` splits the −1 kill sentinel (negative → right → `H`)
from data; the zero and positive arms re-merge in three cells (`v` beside
`X`, `<` below — both land on the same leftward row) onto `+ s`.

**Shutdown.** Producer halts after `0s`; man 1 reads the 0, sends −1,
halts; man 2 reads −1, halts. All men halted, the sim's drain-on-halt
flushes the last bytes out of the output pipe.

## Why 92 × 88

Data dominates everything: 2810 chars ≈ 6890 cells at 22 cells per
9 chars. Width 92 gives an 88-cell data span = exactly 4 slots per row;
313 chunks then need 79 rows, and 79 + 2 walls + 7 rows of decoder
strip = 88. The producer→man 1 pipe turns a corner (`v` then `>`) so
man 1's room starts flush under the producer wall instead of two rows
lower. Man 2's room is positioned so its `` `31` `` backticks sit on
producer *digit* columns — a decoder backtick under a producer backtick
column can chain an unintended vertical pair across the room walls.

Considered and rejected:

- **Dictionary/BPE compression** (extend the alphabet past 95 with codes
  for " and ", "Simon Peyton Jones", …): under the int64 chunk cap the
  bigger base inflates every plain char (log₁₀128 vs log₁₀95) and the
  dispatch cascade + phrase storage eat most of the stream savings —
  ~5% score for a lot of machinery and risk.
- **Huffman via divmod-2 bit stream**: near-entropy data (~3800 cells)
  but each of ~94 tree nodes needs its own bit-extraction sequence;
  the physical tree costs more than it saves.
- **Computing the years** (1996…2026): ~190 chars saved, but emitting a
  4-digit number as characters needs its own divmod loop — roughly a
  wash, and the uniform stream is simpler.

## Numbers

max(92, 88)² = 8464 = score (officially confirmed). 56 246 ticks
(irrelevant to score). Covered by `tests/test_history.py`: exact output,
halting, footprint, official backtick rule, and generator/artifact sync.

## Ideas for improvement

- Values are hard-capped at signed 64-bit (Language Reference), so the
  9-char chunk is already optimal per literal; only a denser layout or
  compression can shrink the grid further.
- The decoder strip has ~50 spare columns; anything that needs more
  machinery (e.g. a second unpacker fed by interleaved chunks) is free
  width-wise but saves no height, so it only pays if it shortens the
  producer.
- The width could drop back toward 88 if the pad cell per slot were
  eliminated by a smarter column scheme (the constraint is only that no
  op sits between two vertically paired backticks — digits between them
  are legal, which a future layout could exploit).
